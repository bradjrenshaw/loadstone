# Loadstone Mod Manager — Package & Manifest Specification

**Draft 1** — `manifestVersion: 1`

This document specifies the package format for Loadstone Mod Manager, a unified,
cross-platform mod manager for game accessibility mods. The `loadstone-packages/`
directory name identifies the format on disk, but the format is open: it is
written so that any conforming client (GUI app, CLI, or a different frontend
entirely) can consume the same packages.

Design goals, in priority order:

1. **No arbitrary code in packages.** Everything a package can do is expressed in a
   small, declarative step vocabulary that the manager implements. If a mod needs
   something new, the vocabulary grows by one reviewed step type — packages never
   ship executable install logic.
2. **Artifacts stay on the author's GitHub releases.** Repositories are just git
   repos of small pointer files. Nobody hosts binaries, and listing a mod is a
   one-time PR.
3. **Accessible by construction.** All UI (install flows, settings forms, action
   buttons) is generated by the manager from manifest data, so screen reader
   behavior is tuned once and inherited by every mod.
4. **The developer CLI and the installer read the same manifest.** One file drives
   release builds, CI, and end-user installs.

---

## 1. Package kinds

Every package file has a `kind`:

| kind      | What it is                                                        | Examples                          |
|-----------|-------------------------------------------------------------------|-----------------------------------|
| `mod`     | An installable mod                                                | SayTheSpire2, Blindfold           |
| `game`    | Shared per-game data: detection, user-data paths, named locations | slay-the-spire-2, balatro         |
| `tool`    | A loader/injector shared between mods                             | lovely-injector, bepinex          |
| `library` | A shared runtime dependency mods can declare                      | prism                             |
| `link`    | A pointer to another registry (§2)                                | a listing in a community registry |

`game` packages have no artifacts and no releases; they are pure data. `mod`,
`tool`, and `library` packages have releases. `link` files make one registry's
packages reachable through another.

---

## 2. Registries

There is exactly one hosting concept. A **registry** is any git source
(typically a GitHub repo) containing a `loadstone-packages/` directory. Every
file in that directory is a package file — either a **full package** (`game`,
`mod`, `tool`, `library`) committed in place, or a **link**:

```json
// loadstone-packages/blindfold.json in a community registry
{ "kind": "link", "source": "github:bradjrenshaw/Blindfold" }
```

A link says: that source is itself a registry, and its packages are reachable
through this one. Because a mod repo carries its own `loadstone-packages/`
directory, *the mod repo is a registry too* — one that happens to also contain
source code. The mod's project manifest and the game package it targets live
side by side:

```
community-registry/
  loadstone-packages/
    blindfold.json          <- link to github:bradjrenshaw/Blindfold
    say-the-spire-2.json    <- link to github:bradjrenshaw/say-the-spire2
    lovely-injector.json    <- full tool package hosted by the registry itself
  index.json                <- generated (below)

bradjrenshaw/Blindfold/     <- the mod repo, itself a registry
  loadstone-packages/
    blindfold.json          <- the mod's project manifest (§5)
    balatro.json            <- the game package it targets (§4)
  src/...
```

Listing a mod in a community registry is a **one-time PR adding one link
file**. Releases, game-data fixes, and new metadata never touch the central
registry again — the author commits to their own repo and every consumer sees
it. Registry maintainers may also host full package files directly: shared
game packages they want to curate, or tool/library packages (like a loader)
whose upstream project doesn't carry a `loadstone-packages/` directory of its
own. A full package file hosted outside the repo its artifacts come from names
that repo in a `source` field; when `source` is absent it defaults to the
registry repo containing the file.

Within one `loadstone-packages/` directory, each package id MUST be defined
exactly once (the file's `id` field is authoritative; filenames are
conventionally `<id>.json` but informative only). Two *links* in the same
registry whose targets define the same id are a conflict with no resolution
order — registry CI MUST fail index generation on such collisions. A link file
MAY carry a `packages` allowlist of ids to constrain what may be resolved
through it, which also gives reviewers an explicit record of what a listing
adds.

### 2.1 Scope: innermost outward

Package references — `"game": "<id>"`, dependency ids — resolve through the
**scope chain**, innermost first:

1. The `loadstone-packages/` directory of the repo the referencing file
   lives in.
2. The registry through which that repo was reached (the one whose link the
   client followed), then *its* parent, and so on outward to the registry the
   user configured.
3. Nothing else. First match wins.

The consequences are the point:

- **A mod author owns their mod's world.** The game package next to the mod
  wins over any copy elsewhere, so shipping a detection fix is a commit to
  the author's own repo — never a PR to someone else's registry.
- **Sharing is omission.** A mod that wants the registry's curated game
  package simply doesn't carry its own copy; the reference falls through the
  chain and finds the registry's file. No qualified-reference syntax exists
  or is needed.
- **Resolution is per discovery chain**, so a mod never resolves through a
  path its author didn't control or its registry didn't review. Copies of a
  game id in unrelated registries can diverge but can never affect each
  other's mods. A repo added directly by URL has a one-element chain and must
  therefore be self-sufficient.
- Game packages and dependencies resolve **live, at install time**, from the
  chain — they are not frozen into releases. Clients cache fetched package
  files for offline use.

Clients MAY offer an explicit developer override ("use this file for game
`<id>`") for testing; overriding MUST NOT happen implicitly. Cross-registry
features like "scan my machine for supported games" may enumerate and merge
definitions by id for display, but installs always use chain resolution.

### 2.2 Releases and fetching

**Release manifests** are unchanged by any of this: `loadstone-release.json` is
generated by the dev CLI / CI at build time and attached to each GitHub
release of a `mod`/`tool`/`library` package. It freezes the project manifest
for one version — `version`, the artifact list with SHA-256 hashes, and the
install/settings/actions blocks — so installing an old release uses that
release's own layout. Clients installing from the release channel use
`loadstone-release.json`, never the repo's current manifest. The latest one for
`github:owner/repo` is fetched from
`https://github.com/{owner}/{repo}/releases/latest/download/loadstone-release.json` — a
plain HTTP redirect, no API token, no rate limit. Older versions and branch
tips use the GitHub API. Private repositories need an account (§15); with
one, every request for that source goes through the API instead.

**Identity binding.** A package's id is bound to its source repo by the link
(or by the `source` field of a registry-hosted package file). Clients MUST
reject a release manifest whose artifacts resolve outside that repo. Registry
review vouches for "this link points at the real author's repo"; each release
is trusted to the author's GitHub account, the same trust users place in the
author today.

**Indexing.** A registry SHOULD run a scheduled job that walks its
`loadstone-packages/` directory, follows links one level, and aggregates
package metadata and latest release info into an `index.json` at the repo
root, so clients can browse and search with one fetch (and CI catches id
collisions, §2). Install-time resolution still follows the live chain.

## 3. The install context and path tokens

Before any steps run, the manager resolves an **install context**:

```
{ platform:     "windows" | "macos" | "linux",
  arch:         "x64" | "arm64",
  distribution: "steam" | "epic" | "gog" | "gamepass" | "itch" | "standalone",
  gameDir:      <detected or user-chosen game folder>,
  userData:     <the game's user-data folder, from the game package>,
  ...game-defined named paths }
```

The **distribution** is how this copy of the game was obtained and is managed —
the axis that determines detection method, binary/DRM variant, and user-data
paths. `itch` means the itch.io app (which has install manifests to detect);
`standalone` means a direct download or offline installer, and doubles as the
answer when a hand-picked folder shows no store evidence — there is no
separate "unknown".

Detection logic (Steam library VDFs, the `SteamPath` registry value, Epic launcher
manifests, GOG registry keys/info files, itch app manifests, Proton prefixes) is
implemented once in the manager; detection *data* comes from the game package (§4).
When detection fails, the user browses to a folder; the manager validates it
against the game's `markers` and infers the distribution from disk evidence
(`steam_api64.dll`, `.egstore/`, `goggame-*.info`), falling back to `standalone`.

**Path tokens**, usable in any path field:

| Token            | Meaning                                                          |
|------------------|------------------------------------------------------------------|
| `${gameDir}`     | The game's install folder                                        |
| `${userData}`    | The game's user-data folder (per platform, from the game package)|
| `${game.<name>}` | A named path defined by the game package (§4)                    |
| `${var.<id>}`    | A value bound by an earlier step (e.g. `pick-directory`)         |
| `${appData}` `${localAppData}` `${localLow}` `${documents}` `${home}` | OS folders |
| `${distribution}` `${platform}` `${arch}` | Context strings, usable in paths and conditions |
| `${steam.appId}` | The game's Steam app id from its game package (`detect.steam.appId`) |

All writes MUST resolve inside `${gameDir}`, `${userData}`, a game-defined path, or
a user-picked directory. Zip entries with absolute paths or `..` components MUST be
rejected. These are engine guarantees, not per-mod responsibilities.

## 4. Game packages

Pure data, no releases. A game package usually lives in the mod repo's own
`loadstone-packages/` directory next to the mod that targets it; a registry
that wants to curate shared game data hosts the file directly instead, and
mods that omit their own copy resolve to it through the scope chain (§2.1).

```json
{
  "manifestVersion": 1,
  "kind": "game",
  "id": "balatro",
  "name": "Balatro",
  "detect": {
    "steam": { "appId": 2379780, "dirName": "Balatro" },
    "markers": ["Balatro.exe"]
  },
  "userData": {
    "windows": "${appData}/Balatro",
    "macos": "${home}/Library/Application Support/Balatro"
  },
  "paths": {
    "mods": "${userData}/Mods"
  }
}
```

- `detect.<distribution>` — per-distribution detection data. A distribution
  absent here means the game is not known to exist there. `markers` validate any
  candidate folder (auto-detected or hand-picked): at least one marker must exist,
  so list each platform's (`Balatro.exe`, `Balatro.app`).
- `detect.steam.appId` — the Steam app id, exposed as `${steam.appId}` so a
  mod's `launch` list can open `steam://rungameid/${steam.appId}` (§5).
- `detect.steam` may also be a list, for a game that ships as more than one
  Steam app a mod supports equally (a demo, a playtest). Every entry is
  detected; a copy is matched to its entry by folder name, which sets its
  `${steam.appId}`, and an entry's `name` is shown in the copy's label
  ("Steam demo copy"). For a made-up game with a separate demo app (the ids
  are placeholders, not real apps):

```json
"steam": [
  { "appId": 9999990, "dirName": "Example Game" },
  { "appId": 9999999, "dirName": "Example Game Demo", "name": "demo" }
]
```
- `userData` — per-platform user-data root, resolved into `${userData}`.
- `paths` — named locations resolved into `${game.<name>}` tokens. Entries may
  themselves use tokens and may be overridden per platform or distribution with an
  object form: `{"default": ..., "when": [{"distribution": "epic", "value": ...}]}`.

Fixing detection for a game fixes it for every mod of that game. This also enables
"scan my machine and list supported games I own" as a manager feature.

## 5. Project manifest

The hand-written package file for a `mod`, `tool`, or `library`, living at
`loadstone-packages/<id>.json` in its repo. It holds everything true across
versions and is also used verbatim when installing from a source tree (dev
channel, linked checkout).

Top-level fields:

| Field             | Req | Description                                              |
|-------------------|-----|----------------------------------------------------------|
| `manifestVersion` | yes | Spec version; this document is `1`                       |
| `kind`            | no  | Defaults to `"mod"`                                      |
| `id`              | yes | Registry-unique slug                                     |
| `name`            | yes | Display name                                             |
| `description`     | yes | One-paragraph description                                |
| `authors`         | yes | List of names                                            |
| `license`         | no  | SPDX identifier                                          |
| `game`            | yes (mods) | `id` of the game package                          |
| `source`          | no  | Repo whose releases carry the artifacts; defaults to the repo containing this file (§2) |
| `pinnedRelease`   | no  | Registry-pinned release for externally released packages (§13.1) |
| `distributions`   | no  | Distribution support declaration (§6)                    |
| `dependencies`    | no  | Tool/library dependencies (§7)                           |
| `channels`        | no  | Install channels (§8); default is `stable` only          |
| `install`         | yes (mods) | Steps to install a **built release** (§9)         |
| `sourceInstall`   | no  | Steps to install from a **source tree** (§8)             |
| `uninstall`       | no  | Extra uninstall steps (§10) — file removal is automatic  |
| `cleanupLegacy`   | no  | Paths from the pre-manager era to delete (§10)           |
| `userData`        | no  | Paths holding user settings, offered for purge (§10)     |
| `settings`        | no  | Settings schema; the manager generates the UI (§11)      |
| `actions`         | no  | Optional named operations with buttons (§12)             |

### 5.1 `launch`

Why users install a mod at all is to play with it, so a manifest can say
how to start the game with the mod loaded. `launch` is an ordered step
list restricted to `run`, `open-url`, `notice`, and `expect` (§9.7–§9.10); it is
frozen into `loadstone-release.json` and into the install record, so the
manager's **Launch** button (and `loadstone launch`) works offline from
state alone. Steps carry `when` like any other, so one list covers every
platform:

```json
"launch": [
  { "step": "open-url", "when": { "platform": "windows", "distribution": "steam" },
    "url": "steam://rungameid/${steam.appId}" },
  { "step": "run", "when": { "platform": "macos" },
    "program": "${gameDir}/Balatro.app/Contents/MacOS/love",
    "cwd": "${gameDir}",
    "env": { "DYLD_INSERT_LIBRARIES": "${gameDir}/liblovely.dylib" } }
]
```

Conditions (§9) let the list pick a route at launch time. Balatro needs the
Steam client running, and on macOS Steam only loads the injector once the
game's Launch Options point at a wrapper, so:

```json
"launch": [
  { "step": "expect", "when": { "distribution": "steam" }, "checks": [
      { "processRunning": ["steam", "steam_osx"],
        "message": "Steam isn't running. Open Steam, then press Launch again." } ] },
  { "step": "open-url",
    "when": { "platform": "macos", "steamLaunchOptions": "steam_lovely_macos.sh" },
    "url": "steam://rungameid/${steam.appId}" },
  { "step": "run",
    "when": { "platform": "macos", "not": { "steamLaunchOptions": "steam_lovely_macos.sh" } },
    "program": "${gameDir}/Balatro.app/Contents/MacOS/love", "cwd": "${gameDir}",
    "env": { "DYLD_INSERT_LIBRARIES": "${gameDir}/liblovely.dylib" } }
]
```

A launch list is offered only while the mod is installed by the manager;
a copy installed some other way has no frozen steps to run.

## 6. Distribution support

```json
"distributions": {
  "steam": "supported",
  "gog": "untested",
  "standalone": "supported",
  "gamepass": { "level": "unsupported",
                "reason": "The Game Pass version keeps game files in a protected folder that mods cannot be installed into." }
}
```

Levels: `supported`, `untested` (installable after an informational prompt),
`unsupported` (blocked, with the reason shown). Omitted distributions default to
`untested` if the game package can detect them, else they simply never come up.
Declaring `standalone` support says DRM-free copies (itch downloads, offline
installers) work when the user points the manager at the game folder.

---

## 7. Dependencies

```json
"dependencies": [
  { "id": "lovely-injector", "version": ">=0.8" }
]
```

Dependencies are `tool` or `library` packages resolved from the same registries.
The manager installs them per-game, tracks their versions, reference-counts them
(a tool is not removed while any installed mod needs it), and applies the tool's
own conflict policy — e.g. lovely-injector declares `"conflictPolicy": "keep-newer"`
so an existing newer injector installed outside the manager is never downgraded.
Tool installs that write into `${gameDir}` may require elevation; the manager owns
that prompt and its error messaging.

Version constraints use standard semver range syntax. Omitted `version` means
"latest".

## 8. Channels and sources

```json
"channels": {
  "stable":     { "source": "release" },
  "prerelease": { "source": "release", "includePrereleases": true },
  "dev":        { "source": "branch", "branch": "main" }
}
```

The user picks one channel per installed mod. Per-channel semantics:

- **`release`** — versions are release tags, compared by semver (leading `v`
  tolerated). Artifacts are hash-pinned by `loadstone-release.json`. This is the default and
  the only channel if `channels` is omitted.
- **`branch`** — installs the branch zipball; version identity is `"<branch>@<sha>"`
  and "update available" means the stored sha is no longer the branch tip. The
  manager strips the zipball's single top-level folder, reads the project
  manifest from the tree's `loadstone-packages/` directory, and runs its
  **`sourceInstall`** steps. Only meaningful for mods whose
  source tree contains the payload (interpreted mods, or repos that commit build
  outputs). Branch installs cannot be hash-pinned; the manager labels the channel
  as trusting the repo tip.
- Compiled mods that want a dev channel SHOULD publish a rolling prerelease from CI
  (e.g. a `nightly` tag with `loadstone-release.json`) instead:
  `{ "source": "release", "tag": "nightly" }`. This keeps hash pinning.

A third source exists outside channels: **local**. "Install from file" (a zip picked
by the user, using the release install steps) and **linked checkout** (the dev CLI
links the install location to a working copy; the manager shows "development
install — managed externally", disables install/update, and uninstall removes only
the link).

## 9. Install steps

`install` (and `sourceInstall`, and action/uninstall step lists) is an ordered list
of steps. The engine provides progress reporting, error surfacing, and rollback of
tracked writes on failure.

Fields common to every step:

- `when` — condition object; the step is skipped unless it matches.
- `requires` — precondition that must hold before the step runs: a condition
  object plus `onMissing` (the message shown when it doesn't hold) and
  `retryable`, e.g.
  `{ "fileExists": <path/glob>, "onMissing": <message>, "retryable": true }`.
  Without `retryable` the step list stops there with the message. When
  `retryable`, the manager shows the message with Retry/Skip options — the
  generalization of "launch the game once, then retry".

A **condition object** holds when every key in it holds:

| Key | Holds when |
|---|---|
| `distribution`, `platform`, `arch` | the context value is the string, or one of the list |
| `fileExists` | the path/glob matches at least one file |
| `processRunning` | a process with one of these executable names (string or list) is running; case-insensitive, a trailing `.exe` ignored (`steam` matches `steam.exe`; Steam on macOS is `steam_osx`) |
| `steamLaunchOptions` | the Launch Options that the most recent Steam user set for the game (`detect.steam.appId`) contain this text; false without an app id, a Steam install, or options. Steam writes them to disk itself, so a change made while Steam runs can take a moment to appear |
| `not` | the nested condition object does not hold |

Conditions are evaluated when the step is reached, so a launch list can
check the machine as it is at launch time.

### 9.1 `extract-archive`

Extracts the current artifact (or source tree) through routing rules.

```json
{ "step": "extract-archive",
  "routes": [
    { "from": "Blindfold/**", "to": "${game.mods}/Blindfold" },
    { "from": "vendor/prism.dll", "to": "${gameDir}/prism.dll" }
  ] }
```

- Supported archive formats: `.zip` and `.tar.gz` (upstream tools commonly
  ship the latter); the format is sniffed from the bytes, not the name.
- `artifact` — the `id` of the release artifact to extract (§13). Absent,
  the step extracts the primary artifact.
- Files whose archive entry carries an executable bit, or whose name ends
  in `.sh`, are written executable (zips built on Windows record no mode).
- `from` — a prefix glob over archive entry paths (`\` normalized to `/`).
  If it contains no wildcard, it names a single file and `to` is the destination
  *file* path; otherwise `to` is a destination *directory* and the path suffix
  after the fixed prefix is appended.
- Entries matching no route are ignored.
- Routes accept `when`.
- Before extracting, the engine verifies at least one route matches something;
  otherwise it fails with "this archive doesn't look like <name>".

### 9.2 `copy-files`

```json
{ "step": "copy-files", "from": "${gameDir}/jaws/*", "to": "${var.jawsDir}" }
```

Same `from`/`to` semantics as routes, over the filesystem.

### 9.3 `ensure-dirs`

```json
{ "step": "ensure-dirs", "paths": ["${game.modifications}/WrathAccess/Assemblies"] }
```

Creates directories (zips drop empty dirs; some loaders require them).

### 9.4 `edit-json`

Structured edits to a JSON file. The engine guarantees: UTF-8 BOM tolerated,
unknown fields and other entries preserved verbatim, atomic write.

```json
{ "step": "edit-json",
  "file": "${game.dataRoot}/OwlcatModificationManagerSettings.json",
  "createIfMissing": true,
  "ops": [
    { "op": "ensure", "path": "SourceDirectories", "value": [] },
    { "op": "append-unique", "path": "EnabledModifications", "value": "WrathAccess" }
  ] }
```

Ops: `set` (assign, creating intermediate objects), `ensure` (set only if absent
or wrong type), `append-unique` (array append if not present), `remove-value`
(remove matching values from an array), `remove-key`. `path` is dotted. `file` may
be a glob — ops apply to **every** match, and `requires.fileExists` fails on zero
matches.

### 9.5 `delete-files`

```json
{ "step": "delete-files", "paths": ["${gameDir}/Tolk.dll"] }
```

Best-effort removal; missing files are not errors.

### 9.6 `pick-directory`

```json
{ "step": "pick-directory", "id": "jawsDir",
  "prompt": "Select your JAWS settings directory",
  "suggest": "jaws-user-settings" }
```

Binds the chosen path to `${var.<id>}`. `suggest` names a manager-known location
(`jaws-user-settings` resolves `%APPDATA%\Freedom Scientific\JAWS\<ver>\Settings\enu`;
more may be added) used as the dialog's starting point.

### 9.7 `expect`

Checks that must hold; failing any aborts (and rolls back) with the given
message. Each check is a condition object (§9) plus its `message`.

```json
{ "step": "expect", "checks": [
    { "fileExists": "${game.modifications}/WrathAccess/Assemblies/WrathAccess.dll",
      "message": "The download didn't contain WrathAccess.dll — the repo may be mid-build." }
  ] }
```

In an install, `fileExists` checks double as evidence of a copy installed
without Loadstone. In `launch`, `expect` is how a list states what must be
true before the game starts (§5.1).

### 9.8 `notice`

Writes a message to the activity log and continues. For the follow-up a
package cannot do for the user — typically a per-platform launch instruction
— so it is read out at the end of the install rather than buried in a README.
Path tokens are substituted; `when` is the usual way to scope it.

```json
{ "step": "notice",
  "when": { "platform": "macos" },
  "message": "Steam does not load Lovely on macOS by itself. In Steam, open Balatro's Properties and set Launch Options to: \"${gameDir}/steam_lovely_macos.sh\" %command%" }
```

The step never fails and writes nothing to disk.

### 9.9 `run`

Starts a program and returns without waiting for it. Meant for `launch`
lists (§5.1). `program` must resolve inside `${gameDir}`, `${userData}`,
a game-defined path, or a user-picked directory: a manifest may start the
game it manages, never an arbitrary binary. `args`, `cwd` (defaults to the
program's folder), and `env` values take tokens.

```json
{ "step": "run",
  "program": "${gameDir}/Balatro.app/Contents/MacOS/love",
  "cwd": "${gameDir}",
  "env": { "DYLD_INSERT_LIBRARIES": "${gameDir}/liblovely.dylib" } }
```

### 9.10 `open-url`

Hands a store launcher URL to the OS, so the game starts through the store
that owns it (Steam's overlay and playtime tracking, Epic's and GOG's
own launch paths). Accepted schemes are the launchers behind the known
distributions; anything else (`https://`, `file://`, ...) is rejected:

| Distribution | Scheme | Example |
|---|---|---|
| steam | `steam://` | `steam://rungameid/${steam.appId}` |
| epic | `com.epicgames.launcher://` | `com.epicgames.launcher://apps/<appName>?action=launch&silent=true` |
| gog | `goggalaxy://` | `goggalaxy://openGameView/<productId>` |
| itch | `itch://` | `itch://games/<id>` |
| gamepass | `ms-xbl-` | Xbox app deep link |

Pair steps with `when: {"distribution": ...}` so each copy of the game
launches through its own store:

```json
{ "step": "open-url", "when": { "distribution": "steam" },
  "url": "steam://rungameid/${steam.appId}" }
```

### 9.11 `merge-universal-binary`

Combines thin Mach-O files, one per CPU architecture, into one universal
binary at `output`, then deletes the inputs (and stops tracking them; the
output is tracked instead). The engine does this itself — end users' Macs
have no `lipo` — and each slice is copied byte for byte, so upstream code
signatures survive.

```json
{ "step": "merge-universal-binary", "when": { "platform": "macos" },
  "inputs": ["${gameDir}/liblovely-arm64.dylib", "${gameDir}/liblovely-x86_64.dylib"],
  "output": "${gameDir}/liblovely.dylib" }
```

This exists for injectors loaded through `DYLD_INSERT_LIBRARIES`: dyld
aborts the game when the inserted library has no slice for the process's
architecture, and whether Steam starts the game natively or under Rosetta
depends on the Steam client, not the machine. Under a tool's `keep-newer`
policy an untracked file already at `output` is kept, like any extracted
file.

## 10. Uninstall, updates, and migration

- **File tracking.** The engine records every file it writes, per package. Updates
  first remove the previous version's tracked files (so stale files never linger —
  no wholesale directory nuking needed), then install. Uninstall removes tracked
  files, then runs the manifest's `uninstall` steps (e.g. de-registering from a
  game's mod list), then offers to purge `userData` paths:

```json
"uninstall": [
  { "step": "edit-json",
    "file": "${game.dataRoot}/OwlcatModificationManagerSettings.json",
    "ops": [ { "op": "remove-value", "path": "EnabledModifications", "value": "WrathAccess" } ] }
],
"userData": ["${userData}/mods/SayTheSpire2"]
```

- **`cleanupLegacy`** — paths placed by pre-manager installers (which the manager
  never tracked). Deleted on every install (so an install made before the
  manager honoured this list is cleaned on its next update) and on uninstall.
  Files or folders; a path outside the game's folders, a root itself, one
  reached through a link, or one holding a file another installed package
  tracks is skipped:

```json
"cleanupLegacy": ["${gameDir}/Tolk.dll", "${gameDir}/nvdaControllerClient64.dll"]
```

- **Repair** — every mod gets a Repair button for free: re-run install for the
  recorded version (hash-verified re-download). A manifest may override with a
  `repair` step list if it ever needs to.

- **Running game.** Before writing into `${gameDir}`, the manager checks whether
  the game's process is running and warns first — replacing per-mod "close the
  game and try again" error strings.

## 11. Settings

The manager renders a settings form from this schema — labels, descriptions, tab
order, and screen reader behavior are the manager's, identical for every mod.

```json
"settings": {
  "storage": { "file": "${userData}/mods/SayTheSpire2/installation.json" },
  "entries": [
    { "id": "screen_reader", "type": "boolean", "default": true,
      "label": "Screen reader support",
      "description": "Enables text-to-speech announcements and keyboard navigation for blind players.",
      "promptOnInstall": true }
  ]
}
```

- `storage.file` — where values are materialized (JSON object keyed by entry ids).
  The mod reads this file at runtime. `format: "json"` is the default and only
  format in v1.
- Entry types: `boolean`, `string`, `number` (`min`/`max`), `choice` (`options:
  [{value, label}]`).
- `promptOnInstall: true` entries are presented as a form on first install
  (cancelling writes defaults). The same schema powers the mod page's settings
  section afterwards.
- Changing settings writes the file immediately; a `note` field (e.g. "Restart the
  game for changes to take effect") is announced after saving.

## 12. Actions

Named optional operations, rendered as buttons on the mod's page.

```json
"actions": [
  { "id": "install-jaws-config",
    "label": "Install JAWS config",
    "description": "Copies JAWS configuration files into your JAWS settings folder.",
    "enabledWhen": { "fileExists": "${gameDir}/jaws/*" },
    "steps": [
      { "step": "pick-directory", "id": "jawsDir",
        "prompt": "Select your JAWS settings directory", "suggest": "jaws-user-settings" },
      { "step": "copy-files", "from": "${gameDir}/jaws/*", "to": "${var.jawsDir}" }
    ] }
]
```

Actions reuse the step vocabulary. `enabledWhen` takes the same condition object
as `when`. Files written by actions are tracked like any others.

## 13. Release manifest (`loadstone-release.json`)

Generated by the dev CLI / CI; attached to every release next to the artifacts.

```json
{
  "manifestVersion": 1,
  "id": "blindfold",
  "version": "0.4.2",
  "game": "balatro",
  "artifacts": [
    { "file": "Blindfold.zip", "sha256": "<hex>" }
  ],
  "install": [ ... ],
  "settings": { ... },
  "actions": [ ... ],
  "uninstall": [ ... ],
  "dependencies": [ ... ],
  "distributions": { ... }
}
```

- `artifacts` — the downloadable files. Each may carry `when` constraints
  (`platform`, `arch`, `distribution`); the manager picks the **first** artifact
  whose constraints match the install context as the primary. An unconstrained
  artifact matches everything — most mods list exactly one. Combinatorial
  variants exist only when binaries genuinely differ per platform or distribution.
- An artifact may also carry an `id`. Every matching artifact with an id is
  downloaded (and hash-checked) alongside the primary, and an
  `extract-archive` step names it with `artifact` (§9.1). This is how one
  install can combine several upstream downloads — for example both macOS
  slices of an injector into one universal binary (§9.11).
- `sha256` is REQUIRED; the manager verifies before installing.
- The embedded blocks are copies of the project manifest's, frozen at build
  time, so a release never depends on the repo's current state. Game packages
  and dependencies are *not* embedded — they resolve live through the scope
  chain (§2.1), so game-data fixes reach already-released versions.
- `installers` — the standalone builds attached to the release (the manager,
  or a mod's branded installer), one per platform:
  `{ "file", "sha256", "loadstoneVersion", "platform" }`, where `platform` is
  `windows` (an `.exe`) or `macos` (a `.dmg` holding one `.app`, as
  `scripts/build_macos_app.sh --dmg` makes it; a `.zip` holding one `.app`
  also works). `loadstone package --installer <file>`
  (repeatable) stamps them, inferring the platform from the file.
  `installer` — a single block with no `platform` — is the Windows entry
  again, for clients that predate `installers`.

  **Self-update.** A running build reads its update source's latest release
  (a manager build: the Loadstone repo; a single-mod build: its mod's release
  source; a profile's `updateSource` overrides) and offers the entry for its
  own platform when that `loadstoneVersion` is newer than its own. It never
  takes another platform's entry. Applying downloads the file and verifies
  `sha256`, then:
  - **Windows** renames the running exe to `<name>.old`, moves the new one
    into place, and relaunches.
  - **macOS** copies the `.app` out of the image (mounted read-only and
    hidden) into a hidden `.<Bundle>.app.update` folder beside the running
    bundle, refuses it unless its `CFBundleIdentifier`
    matches, moves the running bundle into that folder, moves the new one into
    its place, and relaunches it. It refuses up front when the app runs from a
    translocated (read-only) copy or from its own disk image — the user is
    told to move it to Applications — or when it can't write beside the
    bundle.

  The next start removes what the swap left behind (`.old`, or the update
  folder).

### 13.1 Externally released packages (pinned releases)

Some packages — typically tools like a loader — are released by upstream
projects that know nothing about this format: no `loadstone-release.json`, asset names
the community doesn't control. For these, the registry-hosted package file
carries a **`pinnedRelease`** block:

```json
{
  "kind": "tool",
  "id": "lovely-injector",
  "source": "github:ethangreen-dev/lovely-injector",
  "pinnedRelease": {
    "version": "0.9.0",
    "artifacts": [
      { "file": "lovely-x86_64-pc-windows-msvc.zip", "sha256": "<hex>",
        "when": { "platform": "windows" } },
      { "file": "lovely-aarch64-apple-darwin.tar.gz", "sha256": "<hex>",
        "when": { "platform": "macos", "arch": "arm64" } }
    ]
  },
  "install": [ ... ]
}
```

- Clients do **not** fetch `loadstone-release.json` for a package with `pinnedRelease`;
  the block is the release. Artifact selection works exactly as in §13
  (first `when` match against the install context).
- The download URL is
  `https://github.com/{owner}/{repo}/releases/download/{tag}/{file}` using the
  package's `source`; `tag` defaults to `v{version}` and may be overridden
  with an explicit `tag` field for upstreams with other tag schemes.
- `sha256` is REQUIRED, as always. The pin is *registry-audited*: for the
  riskiest package kind (code injected into games), the hash was reviewed in
  a registry PR — a stronger statement than the normal author-trust flow.
- Updates arrive by updating the package file: a maintainer PR, or a
  scheduled registry job that watches the upstream repo, downloads new
  assets, computes hashes, and opens the bump PR (the Scoop/winget
  auto-update model). The registry lags upstream by that review; for loaders
  that release a few times a year this is the right trade.
- `pinnedRelease` and `channels` are mutually exclusive — pinned packages
  have exactly one available version at a time.

## 14. The generated mod page

Clients SHOULD render each mod as one page derived entirely from manifest data:

1. **Status** — name, installed version/channel, latest version, game path with
   Browse fallback, distribution.
2. **Primary buttons** — Install/Update (version picker incl. prereleases, release
   notes shown before proceeding), Uninstall, Repair, Install from file.
3. **Settings** — generated from §11.
4. **Actions** — one button per §12 entry, enabled per `enabledWhen`.

## 15. Accounts and private repositories

Sources whose host supports it (today: `github:`) can be reached with an
**account**: a stored sign-in whose token is presented on requests. This is
what makes a mod in a private repository installable — by anyone the
repository's owner has given access.

### 15.1 Sources and providers

A source string is `<scheme>:<location>`. Each scheme has a provider in the
client that knows how to fetch release manifests and assets, release lists,
branch archives, and single files from the default branch, with or without a
credential. Anything without a known scheme (including Windows paths such as
`C:\mods`) is a local directory. Only `github:owner/repo` exists today.

GitHub specifics: anonymous requests keep the plain, unrate-limited endpoints
(§2.2). With a token, requests use the REST API on `api.github.com` (release
lookup by tag or latest, then the asset download with `Accept:
application/octet-stream`; `/zipball` for archives; `/contents` for single
files). The token is sent only to `api.github.com`; it is never forwarded
when an asset download redirects to storage.

### 15.2 Loadstone settings

Loadstone keeps its own preferences, separate from a mod's settings form
(§11), in two scopes:

- **Global** — Loadstone-wide. In a standalone single-mod installer, "global"
  means that installer: its settings and accounts are its own.
- **Per mod** — Loadstone's preferences about one mod, keyed by package id.

Each preference is declared once (type, default, label, and whether it is
global, per mod, or global with a per-mod override). A value for a mod is
looked up mod, then global, then default. Storage is under the local data
directory: `Loadstone/settings.json` and `Loadstone/mods/<id>/settings.json`
for the manager, the same layout under `Loadstone/installers/<mod-id>/` for a
standalone installer. Unknown keys are preserved; a value of the wrong type
is ignored.

Current preferences: `accounts` and `accountRules` (global, edited through
the accounts UI), `tryOtherAccounts` (global, default on), and
`downloadAccount` (per mod, default automatic).

### 15.3 Accounts

An account records its provider, host, a user-chosen label, the user name
the token belongs to, and whether it is that provider's default. Tokens are
never written to settings files: they live in the OS credential store
(Windows Credential Manager, macOS Keychain) under the service `Loadstone`,
user `manager/<account-id>` or `installer/<mod-id>/<account-id>`.

Accounts are added by browser sign-in (OAuth device flow: Loadstone shows a
short code, the user enters it on the site and approves) or from an existing
token, which is checked with the site first. Signing in again as the same
user refreshes that account's token. On GitHub, Loadstone's OAuth App asks
for the `repo` scope, the only OAuth scope that can read private
repositories. It grants read **and write** access to the user's
repositories; Loadstone only ever reads with it. Removing an account deletes
its token locally; revoking the app's access is done in the site's own
settings.

An **account rule** pairs a pattern (a source such as `github:owner/repo`, or
an owner wildcard such as `github:owner/*`) with an account.

### 15.4 Choosing credentials for a request

For each request, the client tries credentials in this order:

1. A token from the environment (`LOADSTONE_GITHUB_TOKEN`, `GH_TOKEN`,
   `GITHUB_TOKEN`), for CI and scripts. Explicit: nothing else is tried.
2. The mod's `downloadAccount`, when set. Explicit.
3. The most specific matching account rule (a repository beats an owner).
4. The provider's default account.
5. No credentials.

When a choice from steps 3–5 is refused (HTTP 401, 403, or 404) and
`tryOtherAccounts` is on, the provider's other accounts are tried next. An
anonymous "not found" is reported as possibly private, with a hint to sign
in; the GUI offers to.

## 16. Security model

- **No package code executes.** The step vocabulary is the entire capability
  surface. New capabilities require a manager release, which is code-signed once
  per platform.
- **Writes are confined** to the game dir, the game's user data, game-declared
  paths, and user-picked directories. Path traversal in archives is rejected.
- **Release artifacts are hash-pinned** by `loadstone-release.json`; identity is bound to the
  author's repo by the link (or `source` field) that reached it. Branch (dev)
  channels are explicitly labelled as trusting the repo tip.
- **Registries are federated.** The default community registry reviews link PRs;
  anyone can add another registry by URL and owns that trust decision. References
  resolve only through the discovery chain (§2.1), never across unrelated
  registries.
- **Tokens stay in the OS credential store** and are sent only to the API
  host of the provider they belong to (§15). They never appear in settings
  files, logs, or release manifests.

## 17. Versioning of this spec

`manifestVersion` is a single integer. Clients MUST refuse manifests with a higher
version than they understand (prompting for a manager update) and SHOULD accept all
lower versions. Additive fields within a version are allowed; unknown fields MUST
be ignored.
